# M4.10.4 (Repsanity) Manual Verification Checklist

1. Generate a test seed with `repsanity_expansion_pools`/`repsanity_rank_tier_pools` at their defaults (both full vocabularies) and `check_density: 100`. Confirm the generated datapackage includes locations named `Reputation: Bloodsail Buccaneers (Hostile)` and `Reputation: Stormwind (Friendly)`.
2. Start a local server + client against that seed (`docs/guides/dev-cheat-sheet.md`'s "How do I generate a test seed?"). Use a GM command to set reputation with Stormwind to Friendly (`.modify reputation 72 <value-past-Friendly-threshold>` or the equivalent in-game rep-gain action). Confirm the AP client log shows a location check fire for `Reputation: Stormwind (Friendly)` the instant the rank changes, not before.
3. Repeat for a negative-capable faction: set reputation with Bloodsail Buccaneers from its real Hated starting value up past the Hostile threshold. Confirm `Reputation: Bloodsail Buccaneers (Hostile)` fires, and that it did NOT fire at any point while still in the Hated range.
4. Confirm a single large reputation gain that crosses two rank boundaries at once (e.g. a GM command jumping straight from Hostile to Neutral) fires BOTH intervening locations (`Reputation: <Faction> (Unfriendly)` AND `Reputation: <Faction> (Neutral)`). **Pre-verified during SDD execution (2026-08-30), not an open question:** the real AzerothCore engine (`ReputationMgr::SetReputation`, `ReputationMgr.cpp:416-444`) computes `old_rank`/`new_rank` once each and fires `OnPlayerReputationRankChange` exactly once per call with no loop over intervening ranks — confirmed by direct source read. This means the hook itself, not the engine, is responsible for not skipping intermediate ranks. `ArchipelagoRepsanityScript.cpp`'s `OnPlayerReputationRankChange` was found to have exactly this bug (checking only `newRank`) and was fixed (commit `773bce2`) to scan every rank in `(oldRank, newRank]`, mirroring `ArchipelagoProfessionScript.cpp`'s own skill-threshold range-scan — independently re-verified against the fix diff and the real engine source. This checklist item is now a **regression check**: confirm the fixed behavior still holds on a live server before this branch is considered fully field-verified, not a bug hunt.
5. Confirm setting `repsanity_rank_tier_pools` to `{standard}` only (excluding `negative`) regenerates a seed with zero Hated/Hostile/Unfriendly Repsanity locations, and every Neutral+ location still present.
6. Confirm `test_content_freshness` and the full `pytest worlds/wow` suite are green on the final commit.
7. **Carried forward from Task 5's review (open item, not yet done as of this checklist's writing):** run a real `cmake --build ... --target worldserver` (full reconfigure if needed) from an environment with unsandboxed access to the `azerothcore-wotlk` checkout, to confirm `ArchipelagoRepsanityScript.cpp` links cleanly into the actual server binary. Every task in this milestone that touched C++ was verified via real MSVC compile-only checks against grep-verified stub headers (which did catch two real bugs — a namespace mismatch and a missing multi-rank-jump loop — so this is not unverified code), but no full link-time build has been run against this branch's code. This is the one remaining verification step that requires access this SDD session's sandboxed subagents did not have.
